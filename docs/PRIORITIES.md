# Dez melhorias prioritárias do Thcode

Diagnóstico baseado no código do repositório `rlkbiloga-coder/Thcode`. Prioridades não representam comprovação de falha em produção: configurações Railway e credenciais atuais não foram consultadas. Alterações nesta expansão devem ser revisadas em branch antes do merge e do deploy.

1. **Crítico: substituir chaves expostas e proteger Secrets.** Revogue no provedor qualquer chave real compartilhada no chat e atualize Secrets/Variables do Railway. Não altere `THCODE_API_TOKEN` sem coordenar a troca no frontend. O `.gitignore` passou a excluir `.env` e variantes, mantendo exemplos; isso não revoga chaves nem remove histórico já publicado.
2. **Crítico antes de uso multiusuário: isolamento de execução e autenticação individual.** O terminal local e `/api/run` executam dentro do container do backend. O terminal herda `process.env` em `backend/src/terminal.js`, que pode conter credenciais. Um token de proprietário único não isola clientes. O E2B existente é um caminho para isolamento, mas não substitui automaticamente as rotas locais. Não abrir o serviço para múltiplos usuários sem corrigir esse desenho. Revisar também os caminhos de `backend/src/run.js` e `backend/src/git.js`: execução e clone não usam o mesmo confinamento de `wsPath` aplicado às rotas de filesystem.
3. **Alto: consistência do build Railway.** Sincronizados Dockerfiles da raiz e do backend com Node 22 e Bash explícito, e removida a indicação `rootDir=backend` do README. Contexto esperado: raiz `/`, config `/railway.json`, Dockerfile `backend/Dockerfile`. O validador Python detecta regressões; ajustes no painel Railway ainda dependem de verificar sua configuração real.
4. **Alto: verificar Postgres e Redis reais.** O código já conecta e sinaliza `disabled`, `disconnected` e `ready`. Configure referências de variáveis dos serviços no Railway e valide `/api/infrastructure` autenticado. HTTP 200 em `/api/ready` pode ocorrer com serviços opcionais desabilitados; não prova integração completa. Não há prova atual de credenciais recusadas nesta inspeção.
5. **Alto: volume e recuperação dos arquivos.** `WORKSPACE_DIR=/app/workspace` precisa de volume gravável pelo usuário `node`. Sem isso, o workspace pode desaparecer em redeploy. Implementar e testar backup e restauração, não apenas verificar existência do volume. Não foi provisionado volume nesta mudança.
6. **Alto: validar E2B e webhook ponta a ponta.** SDK, checagem de namespace, assinatura de corpo bruto e deduplicação Postgres já existem. Registrar webhook HTTPS do backend, configurar segredo no Railway, criar/encerrar um sandbox real e comprovar entrega/reentrega. Testes unitários não comprovam a conta do provedor. E2B pode gerar custos; nada foi acionado nesta expansão.
7. **Médio: contratos tipados para novas funções.** Adicionado cliente TypeScript somente leitura de readiness em `packages/api-client`, com compilação e sete testes. Evoluir rotas com tipos e validação de entrada antes de integrar outras plataformas. Não é migração do backend inteiro para TypeScript.
8. **Médio: manutenção automatizada e diagnósticos.** Adicionados verificador Python de deploy, smoke Bash sem credenciais e onze testes Python/shell. CI inclui um job independente de manutenção. Checks locais verificam arquivos e respostas controladas, não o deploy real. O job Docker existente somente constrói a imagem; falta um smoke de container iniciado. Planejar expurgo de IPs vencidos no mapa do rate limiter (`backend/src/security.js`) e timeout de sessões SFTP (`backend/src/sftp.js`) para evitar acúmulo de recursos.
9. **Médio: auditoria e evolução controlada do banco.** Adicionada consulta SQL somente leitura de eventos E2B, com timeout e transação read-only. A tabela precisa existir. Introduzir migrações versionadas e política de retenção posteriormente. A consulta não foi executada contra um banco de produção.
10. **Básico: documentação e integrações complementares sem duplicar infraestrutura.** Frontend e GitHub Pages já existem. Cloudflare pode ser opção de DNS/proteção após estabilizar Railway; Vercel não é necessário para o backend atual. n8n e outros serviços só devem entrar com uma finalidade definida, autenticação e limites de custo. Esta expansão criou organização para novas funções, não conectores automaticamente ativos.

## O que pode ser usado agora
No código desta expansão: ferramentas Python/Bash, cliente TypeScript e consulta SQL (esta última depende de banco acessível). Na configuração existente: frontend GitHub Pages e backend Railway, cuja operação ao vivo ainda precisa ser verificada. GitHub já foi acessado nesta sessão; isso não autoriza nem configura automaticamente credenciais do backend.

E2B, Postgres, Redis, GitHub no backend e provedores de IA têm implementações existentes, mas exigem credenciais/configuração e validação específicas. Cloudflare, n8n e outras plataformas não foram conectadas nem provisionadas. Não há uso gratuito ilimitado garantido.
